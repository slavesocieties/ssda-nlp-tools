# `verify_blocking` on the corpus that actually runs — 2026-08-13

Every published blocking figure, including HANDOVER §7a, was measured on
`production/luna_v3/assembled` — the **raw** assembly. `assembled_deduped` became
the default on 2026-08-12. Those are different corpora and the numbers are not
interchangeable, so this closes the gap.

```
python verify_blocking.py --assembled production/luna_v3/assembled_deduped
```

| | raw (§7a, 2026-08-10) | **deduped (the default)** |
|---|---:|---:|
| mentions | 39,697 | 39,453 |
| enumerated by the legacy scan | 24,035,941 | 23,562,009 |
| generated by keyed blocking | 14,664,254 | 14,466,312 |
| dropped vs the old candidate set | 3,471,975 | **3,386,595** |
| ...refused anyway | 3,106,681 | 3,027,405 |
| ...lifespan-vetoed | 348,405 | 342,360 |
| ...both-sacrament-principals | 16,889 | 16,830 |
| ...would have gone to review | 0 | **0** |
| ...would have AUTO-MERGED | 0 | **0** |
| oversized keys | 0 | 0 |
| names denied the time key | 1 | 1 |

**Keyed blocking is lossless on the default corpus too.** Zero merges and zero
review pairs lost, and still only one name common enough to be denied the time
key.

Worth stating plainly because the losslessness has lapsed once before, silently,
and was restored: this is the property re-verified against the configuration that
actually ships, not against the one it was originally measured on.

The §13(b) caveat is unchanged and still the thing to watch: **one name denied the
time key is a 7-volume result and will not hold at 3,900.** Re-run this on the
next substantially larger corpus before trusting the zeros again — and the rule
is now "whenever the scorer OR the extracted relations move", not just the
weights.
